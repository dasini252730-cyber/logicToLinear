# 작업 루프 (task 하나를 끝내는 순서)

모든 코드 작업은 이 순서를 따른다. 단계를 건너뛰지 않는다.

1. **브랜치 확인**: `main`이면 작업하지 않고 사용자에게 `dev`로 전환을 요청한다. SessionStart hook이 알려 준다.
2. **task 선택**: `node scripts/backlog.mjs next`. 사용자가 id를 주면 그것을 쓴다.
3. **브리핑**: `task-briefer` 서브에이전트에 task id를 넘겨 `docs/tasks/<id>.md`에 "작업 브리핑"을 쓰게 한다. 브리핑을 읽고 범위·관련 파일·줄 수 상한을 확인한다. 브리핑과 요구사항이 다르면 코드를 쓰기 전에 사용자에게 묻는다.
4. **시작**: `node scripts/backlog.mjs status <id> in_progress`.
5. **구현**: 브리핑의 "관련 파일"만 건드린다. 새 파일은 brief에 적힌 예상 경로를 따른다. 줄 수 경고(85%)가 나오면 분리 계획을 세우고, 초과(100%)면 멈추고 분리한다.
6. **테스트**: 완료 조건에 테스트가 있으면 먼저 테스트를 쓴다. 순수 로직은 반드시 단위 테스트.
7. **적대적 리뷰**: `adversarial-reviewer` 서브에이전트에 task id와 변경 파일 목록을 넘긴다. 보고의 "차단" 항목은 모두 고친다. "경고"는 고치거나 사유를 작업 메모에 적는다. "질문"은 `needs_human`으로 올리거나 사용자에게 묻는다. 차단이 0이 될 때까지 반복한다. 반복은 3회까지, 그 이상이면 사용자에게 상황을 보고한다.
8. **기록**: `docs/tasks/<id>.md`의 "작업 메모"와 "결과"를 채운다. 리뷰 보고의 요약(판정 줄과 차단·경고 처리 결과)을 "적대적 리뷰" 섹션으로 붙인다.
9. **리뷰 요청**: `node scripts/backlog.mjs status <id> review`. hook이 lint·build·테스트를 돌린다. 실패하면 고치고 다시 시도한다.
10. **보고**: 사용자에게 무엇을 만들었고 어떻게 확인하는지, 실기기에서 볼 것은 무엇인지 알린다. `done`은 사용자가 확인한 뒤에 찍는다.

## 서브에이전트 사용 규칙

- `task-briefer`(haiku): task를 **시작하기 전에 반드시** 한 번. 브리핑이 이미 있고 그 뒤 코드 변경이 없었으면 다시 부르지 않는다. 비용이 싼 모델이므로 조사만 맡기고 판단은 맡기지 않는다.
- `adversarial-reviewer`(opus): 파일을 **생성·변경한 뒤 review로 올리기 전에 반드시** 한 번. 큰 변경(파일 3개 이상 또는 150줄 이상)이면 중간에 한 번 더 부른다. 리뷰어는 코드를 고치지 않으므로 수정은 메인 세션이 한다.
- 두 에이전트 모두 `backlog.json`을 직접 열 수 없다. CLI만 쓴다.
- 서브에이전트 보고를 사용자에게 전달할 때는 요약하되, "차단" 항목은 빠뜨리지 않는다.
- 문서만 바꾸는 작업(md, json 설정)에는 리뷰어를 부르지 않아도 된다. 단, `docs/요구사항.md`를 바꾸는 작업은 반드시 사용자 확인.

## 세션 시작 시

- hook이 브랜치와 `next` 요약을 보여 준다. `in_progress` task가 있으면 그것을 먼저 이어서 한다.
- 이어서 할 때는 `docs/tasks/<id>.md`의 브리핑·작업 메모를 먼저 읽는다.
