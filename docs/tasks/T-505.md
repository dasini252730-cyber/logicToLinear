### 쉽게 말하면
가져오기 화면에서 사용자가 "덮어쓰기" 옵션을 선택했을 때, 앱의 모든 기존 데이터(Book, Quote, Discussion, Analysis 테이블)를 삭제하고 백업 파일의 모든 데이터를 그대로 넣는다. 중간에 삽입이 실패하면 전체를 롤백해서 원래 상태로 돌린다(트랜잭션 사용).

### 요구사항 원문에서
- `백업`: "가져오기: (...) '기존 데이터를 지우고 덮어쓸까요, 합칠까요?' 선택. 합치기는 isbn13 또는 제목+저자가 같은 책을 같은 책으로 보고 글귀를 추가한다." — 덮어쓰기 vs 합치기. 이 task는 덮어쓰기만 구현
- `데이터 모델 / Book`: "필드 (...) id | Long PK | 자동 증가" — 백업의 Book id를 그대로 복원하지 않고, 새로 자동 증가시킬지 vs 기존 id를 보존할지 결정 필요

### 주의할 점
- **트랜잭션**: withTransaction { ... } 블록 안에서 모든 삭제·삽입을 수행. 중간에 Exception이 나면 자동 롤백.
- **DAO 메서드**: deleteAll() 또는 @Query("DELETE FROM book")과 같은 일괄 삭제 메서드가 필요하면 T-106(DAO 정의)에서 추가하거나 여기서 추가. 각 테이블마다 필요.
- **ID 처리**: 백업 파일의 Book id를 보존할지(예: Book id=1, 2, 3 유지) vs 새로 자동 증가시킬지(예: 삽입하면 1, 2, 3 새로 배정) 결정. 요구사항에 명시 없으므로, 간단히 하려면 id=0으로 설정해 새로 배정받게 하거나, 원본 id를 보존 가능. FK는 Quote의 bookId가 새로운 Book id와 맞아야 함. 일단 원본 id 보존이 자연스러움 (삽입 실패 방지).
- **삽입 순서**: CASCADE 설정에 따라 Book → Quote → Discussion → Analysis 순서로. 요구사항 "Book 삭제 시 함께 삭제"는 CASCADE 설정이므로, 삽입은 역순(또는 ID 무결성을 고려한 순서)으로.
- **완료 조건 "FK 관계 재연결"**: 백업 파일의 Quote.bookId=1이면, 복원된 Quote.bookId도 새로운 Book 중 같은 책(원래 id=1이던 것)을 가리켜야 함.

### 완료 조건 체크 방법
- 테스트: Robolectric으로 Book 2개, Quote 3개를 가지는 백업 파일 생성 → replaceWithBackup() 호출 → bookDao().getAll().size == 2, quoteDao().getAll().size == 3 확인
- 테스트: Quote의 bookId가 실제로 존재하는 Book의 id를 가리키는지, 쿼리로 JOIN 확인
- 시뮬레이터: 앱에서 몇 책을 만든 후 백업 → 다른 백업(다른 내용)을 가져오기 "덮어쓰기" 선택 → 새로운 내용으로 완전히 바뀌었는지 서재에서 확인
- 시뮬레이터: 가져오기 중 오류 시나리오(예: 저장소 권한 오류), 기존 데이터가 유지되는지 확인 (롤백)

## 작업 메모

(2026-10-05)

- `BackupRepository.overwrite(file)`: `db.withTransaction` 하나. `book` 전체 삭제(Quote·Discussion은 CASCADE) + `analysis` 삭제 → 책을 id=0으로 넣어 새 id를 받고 옛 id→새 id 맵으로 글귀·토론의 bookId를 다시 연결. 맵에 없는(책 없는) 글귀는 버린다.
- 글귀는 `insertAndTouchBook`으로 넣어 책 lastQuoteAt(카메라 홈 기본 책 기준)이 함께 맞춰진다.
- 중간 실패는 예외로 나가고 트랜잭션이 롤백된다. ViewModel은 "가져오기에 실패했어요"로 보여준다.

- 적대적 리뷰 반영: 책이 없는 고아 글귀·토론은 FK 때문에 버린다. 완료 조건 "책·글귀 수가 백업 파일과 같다"는 유효 행 기준이다(테스트의 bookId=999 글귀가 그 예). 책의 lastQuoteAt은 백업 값을 믿지 않고 글귀를 넣으며 다시 계산한다(글귀 없는 책은 null).
