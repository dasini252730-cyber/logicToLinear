## 설명

T-810으로 설정이 토론 위에 하위 화면으로 쌓이게 되면서 생긴 경로. 토론 위 설정에서 JSON 가져오기(DB 교체)를 하면 뒤로가기로 돌아온 토론은 discussion == null → loaded = false가 되어 입력창·'첫 질문 받기'·마무리 안내가 모두 없는 빈 화면(제목만)이 남는다. 크래시는 없고 상단 뒤로가기로 나갈 수 있다. 후보: loaded=false이고 로딩이 끝났으면 '토론을 찾을 수 없어요' 안내 + 뒤로가기, 또는 자동으로 책 상세로 팝.

### 쉽게 말하면
사용자가 토론 화면에서 설정으로 들어가 백업을 가져와 데이터를 교체한 후 뒤로 나가면, 열어둔 토론이 더 이상 없어져서 화면이 텅 빈 상태가 된다. 사용자에게 "이 토론을 찾을 수 없어요" 같은 안내를 보여주고 뒤로 돌려보내거나, 책 상세 화면으로 자동으로 돌려보내는 처리가 필요하다.

### 주의할 점
- 현재 DiscussionScreen은 `!state.loaded` 시 하단 바(입력창, 첫 질문 받기 버튼 등)를 감춘다(line 95). 내용 영역도 비어 있으면 사용자에게는 제목만 보인다.
- 토론이 로딩 중인 상태(초기 진입)와 로딩이 완료되었지만 데이터가 없는 상태(백업 교체)를 구분해야 할 수 있다. 현재는 `loaded = discussion != null`이므로 두 경우 모두 false이다. 시간 경과(예: LaunchedEffect나 stateIn의 WhileSubscribed 타임아웃)를 이용해 구분할 수 있는지 확인 필요.
- 최종 선택(안내 문구 표시 vs 자동 팝)은 요구사항에 명시되지 않았으므로, 작업 중 사용자 지시를 기다리거나 적절한 방식을 선택해야 한다.

## 작업 메모

- 2026-10-23. 사용자 지시: 원인 분석 → 복원 가능 여부 → 필요한 예외 처리.
- **원인**: `DiscussionViewModel.uiState`가 `loaded = discussion != null`만 두어 "아직 DB를 읽지 않음"과 "행이 없음"을 구분하지 않았다. 토론 위에 쌓인 설정(T-810)에서 백업 OVERWRITE를 하면 `BackupRepository`가 `bookDao.deleteAll()`을 부르고 Discussion은 CASCADE로 지워진다. `observeById`가 null을 방출 → loaded=false → 화면의 bottomBar는 `!loaded -> Unit`, 본문은 빈 LazyColumn. 제목만 남는 빈 화면.
- **복원 가능 여부**: 불가. 행이 물리적으로 삭제됐고 새로 들어온 백업의 토론은 id가 다르다. MERGE 모드는 기존 행을 지우지 않아 이 문제가 없다. 그러므로 "복원"이 아니라 "없음을 알리는" 처리가 맞다.
- **처리**: `loaded`("DB를 한 번 읽었다", 방출 시 무조건 true) + `found`("행이 있었다") + `missing` 파생값(`loaded && !found`). 리뷰 경고 1을 받아 `CaptureViewModel`의 `bookLoaded`·`bookMissing`과 같은 꼴로 맞췄다. 처음엔 `loaded = discussion != null` + `missing = discussion == null`으로 두 필드가 서로의 보수이고 "둘 다 false = 로딩 중"이라는 암묵 규약에 기댔는데, 나중에 누가 기본 상태를 다시 방출하면 빈 화면이 그대로 재발하는 구조였다. 화면 요소(턴 표시·입력창·첫 질문 버튼)는 모두 `found`로 판단한다. 화면은 `missing`이면 본문에 "토론을 찾을 수 없어요"(`discussion_not_found`)를 보여 주고 입력창·첫 질문 버튼은 그대로 숨긴다. 뒤로가기는 책 상세로 가며, 책도 지워졌으면 책 상세가 기존 패턴대로 "책을 찾을 수 없어요"를 보여 준다. 자동 네비게이션(서재로 튀기)은 하지 않았다. 백업을 가져온 직후 화면이 저절로 바뀌는 것보다 안내 뒤 사용자가 나가는 쪽이 예측 가능하기 때문.
- 새 문구 "토론을 찾을 수 없어요"는 요구사항 예외 처리 표에 없다. `book_detail_not_found`("책을 찾을 수 없어요") 선례와 같은 형식이며, 사용자가 "필요한 예외 처리를 구현"하라고 했으므로 추가했다. 요구사항 표에 넣을지는 아래 질문.
- 테스트: 수집 전(로딩 중) loaded=false·missing=false → 수집 후 loaded·found → `bookDao.deleteAll()` 뒤 missing=true·found=false·needsFirstQuestion=false·canSend=false. 이어서 `send()`·`requestFirstQuestion()`을 불러도 AI 호출 수가 늘지 않음을 확인한다(리뷰 경고 2: 그 방어선은 `DiscussionRepository`의 null guard인데 테스트가 없었다).
- 리뷰 경고 3(설정에 5초 넘게 머물면 `WhileSubscribed(5_000)` 캐시 때문에 돌아온 첫 프레임에 예전 토론이 한 번 보임): 파생값 전환으로 플래그 모순은 없어졌지만 캐시 자체는 남는다. 그 틈에 전송을 눌러도 Repository guard가 막아 AI 호출은 없고, Room 재쿼리가 끝나면 안내로 바뀐다. 수용.
- 리뷰 경고 4: `discussion_not_found`를 `<!-- 책 상세 -->`에서 토론 문구 블록으로 옮겼다.
- 리뷰 경고 5(AI 응답 대기 중 행이 지워지면 `save`가 좀비 부활·FK 위반): 도달 경로가 없고 범위 밖이라 **T-813**으로 분리.
- 줄 수: DiscussionScreen 148/250, DiscussionViewModel 138/200, DiscussionViewModelTest 199/400.

### 실기기 확인 (2026-10-24, SM-S942N)

- 정상 경로 회귀 확인: 책 상세 → 토론을 열면 첫 질문·"남은 턴 20"·입력창("답을 적어 주세요"·전송)이 모두 보인다. `loaded`/`found` 재작성이 평소 동작을 깨지 않았다.
- **남은 확인(사람)**: `missing` 경로는 백업 가져오기(덮어쓰기)로 기존 데이터를 지워야 재현되므로 실행하지 않았다. 기기에 실제 책·글귀·토론이 들어 있어 임의로 지우지 않는다. 확인하려면 먼저 내보내기로 백업을 받아 두고, 그 파일로 덮어쓰기를 한 뒤 토론으로 돌아와 "토론을 찾을 수 없어요"를 확인하면 된다.
